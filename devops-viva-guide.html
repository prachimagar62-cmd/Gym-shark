1. High-Level Architecture & DevOps Core Concepts
Q1. What is DevOps, and what problem does it solve in this project?
Answer: DevOps is a cultural and technical methodology that bridges software development (Dev) and IT operations (Ops). Traditionally, developers write code and hand it over to operations engineers to deploy manually, causing communication delays, configuration drift, and human errors. In our project, DevOps automates testing, building, server provisioning, and deployment using automated CI/CD pipelines, allowing code pushed to Git to go live within minutes with zero manual server intervention.
Q2. Walk me through the architecture of your deployed application.
Answer: The architecture follows a 3-Tier Production Setup:
  1. Presentation Layer: React (Vite) Single Page Application compiled into static HTML/CSS/JS and served directly by Nginx on Port 80.
  2. Application Layer: Node.js & Express REST API listening internally on Port 5000, kept alive 24/7 by the PM2 process manager.
  3. Data Layer: MongoDB Atlas cloud database cluster (M0 replica set) accessed securely over TLS/SSL from EC2.
  4. Routing: Nginx acts as a reverse proxy, serving the static frontend files for web traffic (/) and transparently proxying API traffic (/api/*) and product images (/image/*) to the Express backend.
Q3. What is the difference between Continuous Integration (CI) and Continuous Deployment (CD)?
Answer:
  • Continuous Integration (CI): The practice of frequently merging code changes into a central repository, where automated builds and tests verify the changes. In our workflow, Job 1 (build) handles CI by checking out the code on GitHub's Ubuntu runner, setting up Node 22, and compiling the React frontend.
  • Continuous Deployment (CD): The automated release and deployment of validated code directly to production environments without human approval. In our workflow, Job 2 (deploy) handles CD by updating the EC2 instance, running database migrations/seeds, and restarting backend services.
2. Infrastructure-as-Code (IaC) & AWS CloudFormation
Q4. What is Infrastructure-as-Code (IaC) and why did you use AWS CloudFormation?
Answer: IaC is the practice of managing and provisioning computing infrastructure through machine-readable definition files rather than physical hardware configuration or manual web console clicking. We used AWS CloudFormation (infra/ec2-instance.yaml) because:
  • Reproducibility: The entire server environment can be replicated identically at any time.
  • Version Control: Infrastructure changes are committed and tracked in Git.
  • Disaster Recovery: If the EC2 server or lab session is terminated, CloudFormation recreates the exact server, security groups, and SSH keys in under 3 minutes.

Q6. What is AWS UserData and when does it execute?
Answer: UserData is a script passed to the EC2 instance during launch that executes only once on the very first boot of the virtual machine, running under root privileges via cloud-init. It is used for bootstrapping the server (installing packages, configuring swap, and initial repository cloning).
Viva Pro Tip: Mention that you used sudo cloud-init status --wait in GitHub Actions to ensure UserData finishes before SSH deploy commands run!
3. CI/CD Pipeline & GitHub Actions
Q7. Why did you design a Two-Job Pipeline (Build on Runner vs. Deploy on EC2)?
Answer: This is a crucial architectural decision:
  • Resource Constraints: An AWS t2.micro instance has only 1 vCPU and 1 GB of RAM. Running npm install and npm run build (Vite/Rollup compilation) on a 1 GB instance can trigger the Linux OOM (Out-Of-Memory) killer, crashing the server.
  • GitHub Runner Power: GitHub's hosted runner provides 7 GB of RAM and 2 fast vCPUs. Building the frontend on GitHub takes ~5 seconds and guarantees zero load on our production server.
  • Artifact Passing: Job 1 uploads the compiled bundle (frontend-dist), and Job 2 only needs to restart services and run the lightweight backend.
Q8. How did you handle secrets and sensitive environment variables?
Answer: Sensitive values like AWS Access Keys, Session Tokens, MongoDB Atlas URIs, and JWT Secrets are stored encrypted in GitHub Repository Secrets. They are never committed into Git source code. During deployment, the workflow dynamically injects them into the EC2 server's local backend/.env file using printf.
Q9. How is SSH authentication between GitHub Actions and EC2 handled securely?
Answer: Instead of manually generating an SSH key pair and pasting private keys across platforms:
  1. CloudFormation generates the key pair via AWS::EC2::KeyPair.
  2. AWS automatically encrypts and stores the private key inside AWS Systems Manager (SSM) Parameter Store.
  3. The GitHub Actions deployment runner uses the AWS CLI (aws ssm get-parameter --with-decryption) to retrieve the private key into a temporary memory file (/tmp/key.pem) with strict chmod 600 permissions.
  4. The runner establishes an SSH connection using appleboy/ssh-action@v1.2.0 and deletes the key file immediately upon completion.
4. Web Server & Reverse Proxy (Nginx)
Q10. What is Nginx and why is it used instead of exposing Express directly to port 80?
Answer: Nginx is a high-performance HTTP web server and reverse proxy. We use Nginx in front of Node.js because:
  • Static Asset Performance: Nginx serves static HTML, CSS, JavaScript, and images with near-zero memory footprint, bypassing the Node event loop.
  • Security: Express is not exposed directly to the public internet; Nginx acts as a shield, dropping malformed requests and preventing denial-of-service attacks.
  • Unified Port 80 Entry: Both the frontend and backend share the single public port 80. Nginx intelligently routes traffic based on URL path.
  • Production Hardening: Supports client max body size controls, gzip compression, and future SSL/TLS HTTPS termination.
Q11. Explain the line: try_files $uri $uri/ /index.html; in your Nginx config.
Answer: In Single Page Applications (SPAs) built with React Router, routing is handled on the client side in browser JavaScript (e.g., navigating to /men or /contact). When a user reloads the page at http:///men, the browser requests the literal file /men from the server. Without try_files, Nginx would return a 404 Not Found error. try_files instructs Nginx: first check if a file named $uri exists, then check if a folder named $uri/ exists, and if neither exists, fall back to serving /index.html so React Router can render the route.
Q12. What is the difference between sudo systemctl reload nginx and restart nginx?
Answer: reload reads the updated configuration files and spawns new worker processes while allowing existing connections to finish gracefully, resulting in zero downtime. restart completely terminates the Nginx master and worker processes and starts them again, which briefly drops all active connections. We always run sudo nginx -t && sudo systemctl reload nginx.
5. Process Management (PM2) & Runtime
Q13. What is PM2 and why is it preferred over nodemon or bare node index.js in production?
Answer:
  • node index.js runs attached to the terminal; closing SSH terminates the app. If the application crashes on an unhandled error, it stays dead.
  • nodemon is intended for local development to watch for file edits; it consumes excessive CPU/memory monitoring the file system.
  • PM2 is a production process manager that daemonizes the process in the background, auto-restarts on unexpected crashes, enables systemd integration to revive on system reboot, logs stderr/stdout to disk, and monitors memory limits (e.g., max_memory_restart: '300M').
Q14. Why is your PM2 config named ecosystem.config.cjs with a .cjs extension?
Answer: In Node.js, when a project's package.json contains "type": "module", Node treats all .js files as ECMAScript Modules (ESM). However, PM2 expects its configuration file to be in CommonJS format (using module.exports = { ... }). Naming the file with the .cjs extension explicitly forces Node to interpret it as CommonJS, preventing the syntax error ReferenceError: module is not defined in ES module scope.
6. Database, Linux Systems & Troubleshooting
Q15. Why did you use MongoDB Atlas instead of running MongoDB inside the EC2 instance?
Answer:
  • Data Persistence: In educational and lab environments, EC2 instances can be stopped or terminated. Running MongoDB locally on EC2 would mean database loss on instance termination. Atlas cloud databases persist independently 24/7.
  • Resource Conservation: Running a database server requires significant RAM and CPU, which would quickly exhaust a t2.micro instance.
  • Managed Services: Atlas handles replica set high-availability, automated patching, TLS encryption, and backups automatically.
Q16. What is a Swap file and why did you configure 2GB of swap on EC2?
Answer: Swap is space on a secondary storage drive (like an SSD/EBS volume) that the Linux operating system uses as virtual memory when physical RAM becomes full. Since the free-tier t2.micro has only 1 GB of physical RAM, allocating a 2 GB swap file (/swapfile) ensures that temporary memory spikes during package installation or system updates do not crash the operating system or trigger the Linux OOM (Out Of Memory) killer.
Q17. If a user reports "502 Bad Gateway" on your live website, what does it mean and how do you fix it?
Answer: An HTTP 502 Bad Gateway error means Nginx is running and received the client's request, but when Nginx attempted to proxy the request to the upstream backend server (Express on Port 5000), Express was not responding.
Troubleshooting steps:
  1. SSH into the EC2 instance: ssh -i key.pem ubuntu@<IP>
  2. Check backend process status: pm2 status
  3. View error logs to see why Express crashed: pm2 logs gymshark-backend --lines 50
  4. Inspect Nginx logs: sudo tail -f /var/log/nginx/gymshark.error.log
  5. Common causes: MongoDB connection failure (wrong URI or Atlas IP whitelist), missing environment variables, or port conflict.
